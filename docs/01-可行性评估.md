# 可行性评估

> 结论先行：**技术可行性高，工程可行性高，产品可行性取决于「模型服务商自由度」这一关键决策。**
> 本项目已完成可运行实现，并通过 51 项自动化端到端验证（真实 Edge 加载扩展）。

---

## 1. 需求拆解与可行性逐项判定

用户提出的核心诉求共 4 项，加上我们主动补充的 4 项。每一项的技术难度与浏览器扩展的适配性差异很大，
下面按「扩展能做什么 / 不能做什么」给出**实测级**结论。

| 需求 | 可行性 | 扩展能做到什么 | 硬性限制 |
|---|---|---|---|
| 修改网站样式 | ✅ 高 | 注入任意 CSS、内置深色/阅读/紧凑预设、隐藏指定元素、按作用域隔离、可完整撤销 | 无 |
| 批量下载站内音视频 | ✅ 高 | 列出页面已加载的全部媒体 URL、批量下载（带登录态 Cookie 与 Referer）；**HLS/DASH 流自动交 companion 用 ffmpeg 合并分片** | DRM 加密流无法下载 |
| 批量下载文档 | ✅ 高 | 按扩展名过滤链接（pdf/docx/xlsx/…）后批量下载；**表格类页面可自动翻页收集每行每列的链接** | 需站点允许下载；部分站点用 Blob 分片 |
| 读取网页内容 | ✅ 高 | 清洗后的 Markdown 正文、标题大纲、元信息、表格、图片列表、链接列表 | iframe 跨域内容需另开标签页 |
| 输出文档 | ✅ 高 | 直接生成 .md / .docx / .html / .txt 并落盘 | docx 样式有限（无表格图片），复杂排版走 companion + pandoc |
| 网页交互（点击/填表/滚动） | ✅ 高 | 选择器或序号定位、真实用户事件触发、自动提交 | 无法过验证码；跨域 iframe 需授权 |
| 跨标签页操作 | ✅ 高 | 列出/新建/切换/关闭标签页 | 无 |
| 本地模型接入 | ✅ 高 | Ollama / LM Studio 走 OpenAI 兼容协议直连 | 需本地服务已启动 |

### 关键限制的诚实说明

**1. HLS / m3u8 流媒体无法用扩展直接下载，但已经通过 companion 解决了。**
m3u8 是播放清单，真实媒体在几十上百个分片里，浏览器无法把它合并成文件；
而且 Chrome 安全策略不允许扩展启动本地进程。

→ 方案（已实现并实测通过）：扩展识别出 `.m3u8` / `.mpd` 后自动转交 companion，
由 companion 调用用户配置的 ffmpeg 合并分片。用户在扩展设置里填 ffmpeg 路径即可，
路径会持久化到 `~/.netbrowserclaw/config.json`。
实测：3 个 TS 分片的真实 HLS 流 → 合并出 duration=3.00s 的可播放 MP4。

**2. DRM 加密内容（Netflix / 爱奇艺会员 / Widevine）无法下载。**
这不是权限问题，是加密设计。任何声称能下载的方案都在绕过版权保护，我们不做，也不建议用户使用。
→ 本项目只处理**用户自身有权访问的内容**。

**3. 扩展权限是用户最大的顾虑。**
本扩展需要 `<all_urls>` 宿主权限（才能在任意站点注入脚本）。这在安装时会触发 Chrome 的高危提示。
→ 缓解：只申请真正需要的权限项、全部代码开源可审计、不做任何遥测、API Key 只存本地。

## 2. 最大的产品决策：模型服务商自由度

你提到 Kimi 插件「没订阅，且不支持换模型服务商」——这恰恰是本项目最重要的差异化点。

市面上的浏览器 AI 侧边栏几乎都是「厂商闭源 + 绑定自家模型 + 需要订阅」的模式：

| 产品 | 模型服务商 | 订阅要求 | 开源 |
|---|---|---|---|
| Kimi 侧边栏（Edge 商店） | 固定 Kimi | 需要 | 否 |
| Perplexity Comet | 固定 Perplexity | 需要 | 否 |
| Dia | 固定 Dia 模型 | 需要 | 否 |
| Sidekick | 固定 | 需要 | 否 |
| **NetBrowserClaw** | **任意 11+ 家，可自定义** | **不需要** | **是** |

### 实测结论：直连可行性因服务商而异

我们在真实网络环境下实测了各服务商的 CORS 响应头（这是「扩展能否直接请求 API」的决定因素）：

| 服务商 | 浏览器直连 | 实测证据 |
|---|---|---|
| DeepSeek | ✅ | 返回 `access-control-allow-origin: chrome-extension://…` |
| Anthropic | ⚠️ | 需加 `anthropic-dangerous-direct-browser-access: true` 头；部分网络下返回 403 |
| OpenAI / Gemini | ⚠️ | 网络出口受限；官方也不推荐浏览器端直连 |

**结论：不能只做「直连」一种模式。** 所以本项目设计了双传输模式：

- **direct（默认）** —— 扩展直接请求 API。零额外组件，开箱即用。
  DeepSeek、Kimi、通义、智谱、硅基流动、OpenRouter、Ollama、LM Studio 等均可直接用。
- **relay（可选）** —— 请求先发到本地 companion（127.0.0.1:8787）再转发。
  解决官方接口拒绝浏览器直连、或本地网络出口受限的情况。

companion 是一个 40KB、零 npm 依赖的 Node 脚本，`node companion/server.mjs` 即可启动。

## 3. 与「browser-use / Claude in Chrome」类方案的定位差异

调研了主流的浏览器 Agent 方案（详见 `03-开源借鉴.md`），它们和本项目**不是替代关系，而是互补关系**：

| 方案 | 形态 | 浏览器访问方式 | 是否接管你的浏览器 | 计费 |
|---|---|---|---|---|
| browser-use | Python 服务 | 自建/云浏览器 | 否（另开浏览器） | 模型自备 + 云浏览器按量 |
| Playwright MCP / chrome-devtools-mcp | MCP 服务 | 另起受控实例 | 否 | 模型自备 |
| Claude in Chrome | 官方扩展 | 官方扩展 + 本地 companion | **是** | 需 Claude 订阅 |
| Stagehand / Midscene | 框架 | Playwright/Selenium | 否 | 模型自备 |
| **NetBrowserClaw** | 开源扩展 | **直接用你的日常浏览器** | **是** | **模型自备，无订阅** |

本项目的独特位置：**接管你日常使用的浏览器 + 不绑定任何模型服务商 + 完全开源**。

并且——本项目能把浏览器能力通过 MCP 暴露出去，成为 MCP 生态的一环：

```
Claude Code / Cursor / Claude Desktop
        │  MCP (stdio)
        ▼
  NetBrowserClaw companion
        │  bridge (HTTP)
        ▼
   扩展 Service Worker
        │  chrome.* API
        ▼
   你正在使用的那个 Edge/Chrome
```

这意味着：你既能用侧边栏里的 AI，也能在终端里让 Claude Code 直接驱动你的浏览器。

## 4. 已验证的工程事实

以下不是推断，是本项目在 **Edge 153.0.4234.48** 上实测并写进自动化测试的结论：

### MV3 的硬性约束（踩过的坑）

| 约束 | 影响 | 本项目的处理 |
|---|---|---|
| Service Worker 无 DOM，`URL.createObjectURL` 不存在 | **所有文档导出与部分下载直接失败** | 改用 `data:` base64 URL 传给 `chrome.downloads` |
| 扩展 CSP 默认禁止 `unsafe-eval` | 内容脚本里 `new Function` 被拦截，`page.eval` 全部失效 | 改由后台用 `chrome.scripting.executeScript({world:'MAIN'})` 执行 |
| SW 空闲约 30 秒被回收 | 长对话/长轮询可能中断 | Agent 循环放侧边栏页面；companion 轮询加心跳保活 |
| `chrome.runtime.sendMessage` 不投递到自身上下文 | 自测无法触发工具 | 测试从侧边栏页面发起调用（贴近真实路径） |
| MV3 禁止远程托管代码 | 不能从 CDN 加载 marked.js 等 | 全部零依赖手写：Markdown 渲染、DOCX/ZIP 生成 |
| `import()` 在 SW 中被规范禁止 | 动态 import 导致死锁 | handlers 抽为独立模块，切断循环依赖 |

### 关于 DOCX 生成

不引入 `docx.js` / `jszip`（体积大、供应链风险），而是手写 ZIP（STORE 模式 + CRC32）与 OOXML。
实测产物经 Python `zipfile` 校验：ZIP 结构有效、全部 XML 可解析、标题/粗体/斜体/行内代码/有序无序列表/引用/代码块均正确保留。

## 5. 风险登记

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| Chrome 商店审核不通过（权限过大/功能过广） | 中 | 拆分「精简版」（无下载）与「完整版」；提供自托管分发 |
| 用户安装时因 `<all_urls>` 权限犹豫 | 中 | 明确说明用途、代码全开源、不做遥测 |
| API Key 泄露 | 中 | 只存 `chrome.storage.local`（不上云、不同步）；relay 模式可让 Key 留在本地 companion |
| 各家模型 API 协议变动 | 低 | 适配层集中在 `providers.js` 一个文件，便于跟进 |
| 站点反爬导致抽取质量下降 | 低 | 抽取器可替换为 Readability/Defuddle（见借鉴文档） |
| Edge 与 Chrome 的 API 差异 | 低 | 所用 API 均为 Chromium 通用；已在 Edge 实测 |

## 6. 结论

**可以做，而且已经做出来了。** 关键不在于技术难度，而在于三个产品决策：

1. **不绑定模型服务商** —— 这是相对 Kimi 等闭源产品的核心差异化，也是用户最直接的诉求。
2. **不要订阅** —— 用户自带 Key，扩展只做「大脑与手」的连接层。
3. **零依赖、可审计** —— 全部源码可读，无遥测，MIT 许可，便于社区贡献与二次分发。

配套的差异化能力：**MCP 双向**——既是侧边栏助手，也能作为 MCP server 被外部客户端驱动，
这让项目从「一个插件」变成「浏览器能力的基础设施」。
