## 1. 浏览器 AI 助手 / Agent 形态

### browser-use — `browser-use/browser-use`
- **形态**：Python 库 + CLI + MCP server
- **许可**：MIT（需核对）
- **借鉴点**：
  - `browser-use/plugins` 仓库（已核实，`main` 分支）说明了当前生态的连接方式：
    通过 `uvx browser-use@latest --cli-mcp` 暴露 **MCP server**，挂载到 Claude Code / Cursor / Kimi Code
  - 它证明了「用 MCP 把浏览器能力给任意宿主」这条路径是社区共识
- **与本项目的关系**：**互补而非替代**。
  browser-use 另起一个受控浏览器实例（云或本地），本项目直接接管用户**日常使用**的浏览器。
  本项目的 companion 也实现了 MCP stdio，可以挂到同样的宿主里。

### Claude for Chrome — Anthropic 官方
- **形态**：官方扩展 + 本地 companion
- **借鉴点**：**「扩展 + 本地 companion」的双层架构**是最成熟的生产级方案。
  本项目沿用了这个结构，但把 companion 的职责扩展为：反向代理 + 双向桥接 + MCP server。
- **差异**：Claude for Chrome 需要订阅且绑定 Claude；本项目不绑定任何服务商。
- **注意**：`anthropics/claude-for-chrome` 仓库当前 404（未找到公开仓库），
  其商店版本需自行安装体验。

### Chrome DevTools MCP — `ChromeDevTools/chrome-devtools-mcp`
- **许可**：Apache-2.0（已核实）
- **借鉴点**：官方维护的 MCP server，证明「浏览器能力 MCP 化」是官方认可的方向。
  本项目 MCP 工具命名（`browser_read_page` 等）与它的风格一致，便于用户对照理解。

### Playwright MCP — `microsoft/playwright-mcp`
- **许可**：MIT（需核对）
- **借鉴点**：工具描述的写法范式 —— 工具 description 要写清「什么时候用」，
  而不仅是「是什么」。本项目 `shared/tools.js` 遵循同一原则。

### Stagehand — `browserbase/stagehand`
- **许可**：MIT（需核对）
- **借鉴点**：把「AI 意图」映射到「确定性动作」的设计思路（act/extract/observe 三段式）。
  本项目用工具调用协议达到类似效果，但对普通用户更自然。

### Midscene — `web-infra-dev/midscene`（原 `microsoft/midscene` 已迁移）
- **许可**：MIT（已核实）
- **借鉴点**：UI 自动化中「用自然语言描述操作 + 定位元素」的做法。
  本项目 `page.interactive` 提供带 index 的可交互元素清单，
  模型用 `index` 定位比用脆弱的 CSS 选择器稳健得多。

## 3. 媒体与批量下载

| 项目 | 许可 | 借鉴点 |
|---|---|---|
| `yt-dlp/yt-dlp` | Unlicense（已核实） | **HLS/m3u8 与 DASH 的标准解法**；支持 `--cookies-from-browser` 复用登录态 |
| `aria2/aria2` | MIT（需核对） | 多连接分片下载、断点续传 |
| `GopeedLab/Gopeed`（原 `Gopeed/Gopeed` 已迁移） | MIT（需核对） | 现代下载器 UI，扩展可参考其进度与队列设计 |
| `unclecode/crawl4ai` | Apache-2.0（需核对） | 面向 LLM 的抓取输出格式 |
| `mendableai/firecrawl` | AGPL-3.0（需核对） | 网页转 Markdown/结构化数据的服务化方案 |
| `jina-ai/reader` | Apache-2.0（需核实） | `r.jina.ai` 读取服务，companion 可作可选后端 |

**关于扩展内下载的实现选择**：
本项目采用「页面内 hook（fetch/XHR/PerformanceObserver）+ `chrome.downloads` 落盘」，
而非 `chrome.webRequest`。原因（MV3 实测约束）：
`webRequest` 在 MV3 中只能观察不能拦截，且拿不到 `blob:` 与运行时生成的媒体 URL；
页面内 hook 反而覆盖更全。

**HLS 的处理（已实现）**：`m3u8` 需要合并分片，扩展做不到，且 Chrome 不允许扩展启动本地进程。
所以扩展识别出 `.m3u8`/`.mpd` 后自动转交 companion，由 companion 调用**用户配置的 ffmpeg** 合并：

```
ffmpeg -headers "Referer: …
Cookie: …
" -i <m3u8> -c copy -movflags +faststart -y out.mp4
```

ffmpeg 路径在扩展设置里填，companion 负责持久化与调用（`/config`、`/tools/detect`、`/hls`）。
同时可选接入 yt-dlp 增强下载（`/download` 端点，配置了 yt-dlp 路径时优先使用）。
实测：真实 3 分片 HLS → 合并出 duration=3.00s 的 MP4，ffprobe 可解析。

## 4. MCP（Model Context Protocol）

- 规范：`modelcontextprotocol/modelcontextprotocol`
- 本项目实现：**零依赖手写 MCP stdio server**（JSON-RPC 2.0），
  实现 `initialize` / `notifications/initialized` / `ping` / `tools/list` / `tools/call`
- 桥接方式：MCP 客户端 ←stdio→ companion ←HTTP 轮询→ 扩展 Service Worker → chrome.* API

**为什么手写而不引官方 SDK**：官方 TS SDK 会给零依赖项目带来构建步骤；
且 MCP stdio 协议本身很简单（JSON-RPC 2.0 + 几种固定消息类型），手写反而让扩展体积保持为零。

**参考**：`microsoft/playwright-mcp`、`ChromeDevTools/chrome-devtools-mcp`（均为已核实的真实仓库）。

| 项目 | 许可 | 借鉴点 |
|---|---|---|
| `wxt-dev/wxt` | MIT（需核对） | 现代 MV3 框架，side panel 支持完善；**本项目未采用**，因为它引入构建步骤 |

**本项目不用框架的理由**：零构建意味着「clone 下来加载即用」。
对开源项目而言，贡献者改一行代码刷新浏览器就能看到效果，参与门槛低得多。
代价是失去 TypeScript 编译与 HMR —— 这是明确的取舍。

## 7. 许可证注意事项

本项目计划采用 **MIT**。若后续引入以下代码，需注意：

- `mozilla/readability` — Apache-2.0（可商用，需保留 NOTICE）
- `gildas-lormeau/SingleFile` — **AGPL-3.0**，传染性强，**不可直接复制代码进 MIT 项目**（可作为独立进程/子模块使用）
- `mendableai/firecrawl` — **AGPL-3.0**，同上
- `jgm/pandoc` — GPL-2.0，作为**外部进程调用**（而非链接/内嵌）通常无问题

结论：正文抽取若要换用 Readability/Defuddle（Apache-2.0 / MIT）安全；
SingleFile 与 Firecrawl 若要集成，应以独立进程或可选插件形式提供，并单独标注其许可证。
